# CodexPotter Relay：全自动跨会话开发接力系统

## 一、项目目标

基于 GitHub 开源项目：

https://github.com/breezewish/CodexPotter

进行二次开发，构建 **CodexPotter Relay**。

### 核心目标

让 Codex 在执行复杂、长时间开发任务时，能够自动检测上下文压力，在接近上下文限制时：

**自动保存工作进度 → 自动创建全新 Codex 会话 → 自动恢复工作状态 → 自动继续未完成开发任务。**

整个过程无需用户手动发送“继续”，也不依赖旧会话持续存活。

系统应当能够连续进行多次接力，直到开发任务真正完成。

### 预期效果

1. 用户提交一次开发目标。
2. Codex 会话 A 开始执行。
3. 系统自动记录开发进度。
4. 当上下文接近限制时，自动准备交接。
5. 保存代码状态、任务目标、技术决策、测试结果和未完成事项。
6. 创建全新会话 B。
7. 会话 B 自动读取交接包，验证项目状态，并继续执行未完成工作。
8. 当 B 接近上下文限制时，自动交接给 C。
9. 不断重复，直到开发任务完成。
10. 最终自动停止并生成开发报告。

这里的新会话必须是真正拥有新上下文窗口的 Codex 主会话，不允许用普通摘要、Resume 或 Fork 冒充。

---

## 二、技术原则

1. 尽可能复用 CodexPotter 的 `$loop`、子 Agent 调度和 HANDOFF 机制。
2. 不破坏原项目现有功能。
3. 优先使用官方公开支持的 Codex SDK、App Server、CLI 和 Hooks。
4. 独立 Relay Controller 负责跨主会话接力。
5. SQLite 负责持久化工作链。
6. 原始开发任务必须在多次接力后保持一致。
7. 新会话自动接管执行权，不等待人工发送继续指令。
8. 默认避免重复开发、重复修改文件和重复执行危险操作。
9. 保留现有权限审批、沙箱和账户限制。
10. 优先支持 Windows 11 与 Codex CLI，再集成 Codex Windows 桌面版。
11. 不通过修改 Codex 私有代码来实现接力。
12. 不将后台创建线程和桌面版自动弹出可见聊天窗口混为一谈。

所有 API 和 Hooks 均需根据实际安装版本及官方文档核对。

## 三、基础架构

系统分为以下模块：

### 1. Relay Controller

独立于 Codex 会话运行的本地控制器。

负责：

- 创建和管理工作链。
- 启动 Codex 主会话。
- 跟踪当前活动线程。
- 监测执行状态。
- 在安全边界触发交接。
- 自动创建新线程。
- 自动提交恢复指令。
- 检查交接是否成功。
- 管理失败重试及回滚。
- 检测开发任务是否完成。
- 控制整个自动执行循环。

控制器不能依赖旧 Agent 存活。

同一工作链只能有一个拥有写入权限的主执行者。

### 2. Context Monitor

监测上下文压力。

优先通过官方 App Server Token 使用事件获取真实数据。

默认配置：

- 65%：保存检查点。
- 75%：准备交接。
- 80%：下一个安全边界执行接力。
- 90%：高优先级交接，禁止强行中断正在写入的操作。

以上百分比应当允许修改。

只有同时取得可靠的使用量与上下文容量时，才能计算实际占用比例。

无法可靠获取时，应使用轮次计数、压缩事件和其他可验证信号，不能伪造百分比。

### 3. Relay Memory

使用 SQLite 持久化工作状态。

默认路径：

`%LOCALAPPDATA%\CodexPotterRelay\relay.db`

至少创建：

- chains：工作链信息。
- sessions：主会话和子会话信息。
- events：Hooks 和重要执行事件。
- checkpoints：版本化检查点。
- handoffs：跨会话交接记录。
- task_results：执行与验收结果。

要求支持事务、WAL、数据库迁移、幂等事件处理、检查点校验、多项目隔离和异常恢复。

### 4. Relay Hooks

根据 Codex 实际可用的 Hooks 接口接入状态采集。

优先检查：

- SessionStart
- UserPromptSubmit
- PostToolUse
- PostModelRequest
- PreCompact
- SubagentStop
- Stop
- SessionEnd

记录：

- 当前任务。
- 用户要求。
- 已完成事项。
- 未完成事项。
- 关键技术决策。
- 文件修改记录。
- Git 状态。
- 测试结果。
- 失败原因。
- 下一步任务。

Hooks 只能执行轻量操作。长时间运行的工作必须由控制器负责。

### 5. Handoff Manager

负责接力操作。

标准流程：

**PREPARE → START → VERIFY → COMMIT → CONTINUE**

PREPARE：停止旧会话领取新任务，保存并校验检查点。

START：使用官方支持的接口创建干净的新 Codex 主会话。

VERIFY：新会话校验项目目录、Git 状态、已完成工作及待办任务。

COMMIT：确认新会话成功接管后，更新数据库的活动会话。

CONTINUE：自动执行下一项未完成任务。

任何阶段失败，都必须保留旧检查点，进行有限次数的安全重试或回滚。

### 6. Task Validator

负责检测开发任务是否完成。

判断依据包括：

- 原始任务目标。
- 项目验收条件。
- 构建结果。
- 自动化测试。
- 功能完成状态。
- 尚未解决的问题。

任务真正完成后自动停止循环。

无法自动验证的事项，应明确标记等待人工验收，而不能虚报完成。

# 四、重点新增：低额度自动接力测试系统

这是本次开发新增的重点功能。

**测试自动接力时，不得要求 Codex 通过大量对话或无意义开发把上下文填充到 80%。**

必须设计独立测试机制，支持模拟上下文压力。

## 4.1 模拟触发模式

新增配置：

```yaml
relay:
  context_threshold: 0.80
  checkpoint_threshold: 0.65
  auto_handoff: true

testing:
  enabled: false
  simulate_context_pressure: false
  simulated_usage_ratio: 0.80
  max_handoffs: 3
```

这是一份预期配置结构，具体实现可根据项目调整。

当启用模拟测试时：

- 不需要实际消耗 80% 的上下文。
- 不需要向模型发送大量无意义内容。
- 不需要重复运行长时间任务。
- 直接向 Context Monitor 注入模拟使用率。
- 正常触发 Relay Controller 的接力流程。

测试数据必须明确标记为模拟值，不得混入真实 Token 使用记录。

## 4.2 三层测试机制

必须实现以下三种测试模式。

### Level 1：Mock Test

完全使用模拟 Codex 会话和模拟 API。

验证：

1. 上下文预警逻辑。
2. 交接状态机。
3. SQLite 数据写入。
4. 检查点生成和校验。
5. 新会话创建请求。
6. 自动恢复逻辑。
7. 失败回滚。
8. 防止无限循环。
9. 多项目隔离。

这一级原则上不调用真实模型 API，避免产生真实 Codex 模型用量。

### Level 2：Real Handoff Test

**只模拟上下文阈值，其余操作尽可能使用真实 Codex。**

测试流程：

1. 创建一个临时测试项目。
2. 启动真实 Codex 会话 A。
3. 让 A 完成一个简单、可验证的编程任务。
4. 保存真实检查点。
5. 注入模拟的 80% 上下文使用率。
6. 自动创建真实会话 B。
7. B 自动恢复项目状态。
8. B 完成第二个简单任务。
9. 再次注入模拟触发信号。
10. 自动创建真实会话 C。
11. C 继续完成第三个任务。
12. 再次触发接力至会话 D。
13. D 验证所有任务并生成报告。
14. 检查所有会话之间的任务连续性。

**必须实际创建并运行 A、B、C、D 四个不同的主会话，而不是只模拟会话 ID。**

不能只检查新会话创建成功，必须验证新会话实际执行了未完成任务。

每个会话使用简单而不同的开发任务，避免大量 Token 消耗。

真实模型请求依然消耗 Codex 额度，因此必须支持限定测试轮数、最大模型请求次数、可获得时的 Token 预算，以及超限停止。

### Level 3：Real Context Pressure Test

完成前两层测试后，才进行真实上下文压力验证。

要求：

- 使用真实 Token 数据。
- 验证真实上下文阈值判断。
- 验证自动检查点与压缩前事件。
- 验证真实触发后的自动接力。
- 验证极端情况下的恢复能力。

不得为了达到阈值而无限发送无意义内容。

真实压力测试必须默认关闭，由用户显式开启。

如果可以通过受控的小上下文配置进行测试，应优先验证该方案是否被官方支持；若不支持，不得假设可以修改模型的真实上下文容量。

## 五、测试管理命令

实现以下命令行接口：

```powershell
relay test --mode mock
relay test --mode real-handoff
relay test --mode real-pressure

relay test-handoff --count 3
relay test-report
```

以上是需要开发的新命令，不是 Codex 现有命令。

要求：

- Mock 测试默认不使用真实模型。
- Real Handoff 只模拟上下文压力。
- Real Pressure 需要显式开启。
- 每次测试自动生成独立工作链。
- 临时项目与正式开发项目隔离。
- 保留测试日志。
- 支持人工取消。
- 失败时自动停止。
- 禁止无限自动重试。
- 记录真实模型调用次数以及能够获取的用量信息。

## 六、自动接力的生产环境行为

测试功能不能影响正常使用。

正式运行时：

1. 自动监控实际上下文压力。
2. 自动记录重要开发进度。
3. 自动创建检查点。
4. 达到接力条件后，在安全执行边界停止旧会话领取新工作。
5. 自动创建干净的新主会话。
6. 自动提交恢复指令。
7. 验证项目状态。
8. 自动继续开发。
9. 再次满足条件时重复接力。
10. 完成任务后自动停止。

必须区分：

- Resume：恢复旧线程。
- Fork：从旧线程创建分支。
- New Thread：创建干净的新线程。

正常上下文接力优先使用 New Thread。

不能通过 Fork 旧历史来冒充新上下文。

Codex 桌面版的自动打开聊天窗口和可见会话切换作为独立兼容性任务处理。

不能因为桌面版不支持自动聚焦窗口，就阻止后台自动接力功能的交付。

## 八、可靠性和异常处理

必须处理：

- 控制器异常退出。
- Codex 会话异常结束。
- 网络断开。
- 账户额度耗尽。
- 上下文数据缺失。
- Hooks 未正常触发。
- 交接包生成失败。
- 数据库写入失败。
- 新会话启动失败。
- 项目文件被其他进程修改。
- 多个 Agent 同时写入。
- 连续接力失败。
- 测试流程无法结束。

必须使用安全的状态转换、执行锁、持久化检查点与有限重试机制。

控制器重启后能够根据数据库恢复工作链。

用户手动暂停时不得继续自动发起模型请求。

## 九、实施顺序

### Phase 1：源码与接口审查

克隆 CodexPotter，检查原有循环执行机制、文件结构、依赖、许可证、Hooks 和 Codex 接口。

创建独立开发分支。

### Phase 2：SQLite 和状态保存

实现数据库、工作链管理、检查点、历史记录和异常恢复。

### Phase 3：自动接力控制器

实现新会话创建、任务注入、状态校验、执行权迁移及失败回滚。

### Phase 4：Mock Test

先使用模拟 API 测试接力状态机和数据库，不调用真实模型。

### Phase 5：Real Handoff Test

模拟上下文达到 80%，但真实创建 Codex 会话 A、B、C、D，并验证自动继续开发。

这是首版最重要的验收阶段。

### Phase 6：CodexPotter 集成

把自动接力能力与原有 `$loop` 和子 Agent 工作机制整合，确保不同主会话间能够继续同一条开发链。

### Phase 7：真实上下文监控

接入真实 Token 使用事件与上下文压力检测。

先完成常规监控与异常处理，再在用户允许后执行真实压力测试。

### Phase 8：Windows 安装和交付

完成安装器、中文 README、运行日志、测试报告及恢复指南。
