# 恢复指南 / Recovery Guide

本文件说明控制器异常退出、会话异常结束、交接中断之后如何恢复工作链。
所有恢复动作都以 **SQLite 数据库 + 检查点 + 台账** 为依据，不依赖任何会话仍然存活。

---

## 1. 判断当前状态

```powershell
relay chains              # 所有工作链及其状态
relay status              # 最近一条工作链的详情（会话、交接、检查点、任务）
relay status --chain <id> --events 20   # 追加最近 20 条事件
```

工作链状态含义：

| 状态 | 含义 |
| --- | --- |
| `pending` | 已创建，尚未开始执行 |
| `running` | 正常执行中，某个主会话持有写权限 |
| `handoff` | 正在交接，写权限暂时不属于任何会话 |
| `paused` | 被暂停（人工暂停或 agent 报告 blocked），不会再发起模型请求 |
| `complete` | 原始目标已完成并验收 |
| `stopped` | 因预算耗尽或人工停止而结束 |
| `failed` | 连续失败被终止，需人工处理 |

---

## 2. 控制器异常退出（崩溃 / 被杀 / 重启）

控制器只在前台进程里跑；退出后数据库仍保存着最新状态。

```powershell
relay recover --dry-run     # 先看清楚哪些链需要恢复、执行锁归谁
relay recover               # 逐条恢复并继续执行
relay recover --chain <id>  # 只恢复某一条
```

恢复过程：

1. **执行锁回收**：若锁的持有进程已不存在（同主机 PID 失效），该锁被视为陈旧锁并被接管；
   若锁仍被活进程持有，`relay recover` 会拒绝并行接管，避免双写。
2. **台账读取**：优先读取项目内 `.relay/state.json`；无法解析时回退到数据库里
   **校验和仍然有效的最新检查点**，并把内容写回磁盘（此动作会记录 `state_restored` 事件）。
3. **写权限归属**：`chains.active_session_id` 指向哪个主会话，就从那个会话继续发下一轮指令。
4. **交接中断处理**：若崩溃发生在交接过程中（状态为 `handoff`），恢复时会把未完成的交接标记为
   `failed`，把工作链退回 `running`，并把写权限保留在**原会话**上；PREPARE 阶段写下的检查点不会被删除。

---

## 3. 会话异常结束（线程不可用 / 上下文超限 / 额度耗尽）

| 现象 | 判断依据 | 处理 |
| --- | --- | --- |
| 单轮失败 | 事件 `turn_error`，会话 `state` 回到 `active` | 控制器自动重试，最多 3 次连续失败 |
| 连续失败 | 3 次后工作链转 `failed` | 查看 `relay status --events`，人工修复后 `relay resume` 或新建工作链 |
| 额度耗尽 | app-server 返回 `usageLimitExceeded`，或 `account/rateLimits/read` 显示已到上限 | 工作链停止并记录原因；额度恢复后 `relay resume` |
| 上下文压缩 | 事件 `thread_compacted` | 视为上下文已满的可验证信号，下次安全边界即交接 |

---

## 4. 交接失败

交接是 `PREPARE → START → VERIFY → COMMIT → CONTINUE` 的线性状态机：

- 任一阶段失败都会**保留旧检查点**，并在 `relay.handoff_max_retries`（默认 3）范围内用**全新线程**重试；
- 重试用尽后：若原会话仍可用，工作链回退到原会话并继续（`handoffs.state = rolled_back`）；
  否则工作链转 `failed`，原因写入 `handoffs.error`。

查看细节：

```powershell
relay status --chain <id>
relay history --chain <id> --events
```

## 5. 人工暂停与取消

```powershell
relay pause --chain <id>    # 立即停止发起新的模型请求（正在执行的这一轮会自然结束）
relay resume --chain <id>   # 从暂停处继续
relay stop --chain <id>     # 永久停止该工作链
```

暂停只改变数据库状态，不杀进程：正在等待模型返回的那一轮会结束，之后控制器不再发新一轮。
需要立刻终止进程时，直接结束控制器进程，再用 `relay recover` 接管。

## 6. 项目文件被其他进程修改 / 多写者冲突

- **多写者**：同一工作链用数据库执行锁保证只有一个控制器写者；不同工作链之间靠工作分支
  `relay/<chain_id>` 隔离。
- **VERIFY 阶段会发现外部改动**：交交接验证会比较当前分支与 HEAD 是否与检查点一致，
  不一致则判定"项目被其他进程修改"并重试；重试用尽则回滚。
- **台账被破坏**：`state.json` 无法解析时，控制器回退到最新有效检查点并写回，
  同时记录 `ledger_repaired` 事件。

## 7. 数据库损坏

```powershell
# WAL 模式下的常规一致性检查
python -c "import sqlite3,sys;c=sqlite3.connect(sys.argv[1]);print(c.execute('PRAGMA integrity_check').fetchone())" "$env:LOCALAPPDATA\CodexPotterRelay\relay.db"
```

- 检查点自带 SHA-256 校验：损坏的检查点会被跳过，恢复时自动回退到更早的有效版本。
- 数据库整体损坏时，项目内的 `.relay/state.json` + `HANDOFF.md` 仍然可用：
  用同一个项目重新 `relay start` 会生成新工作链，历史记录丢失但代码与台账不受影响。
