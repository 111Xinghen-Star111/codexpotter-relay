# 未验证与已知限制

本文件记录 CodexPotter Relay 当前**没有验证过**、**验证不了**或**实现与需求文字存在差异**的地方。每条按「现象 / 原因 / 当前替代方案 / 如何验证」四段书写，避免把「模拟通过」说成「真实通过」。

状态图例：

- **待验证**：实现存在，但结果依赖真实 Codex 额度、账号、网络或人工开启，当前没有可引用的当次记录。
- **未实现**：需求提到，但代码中尚不存在对应能力。
- **行为差异**：实现与需求文字不完全一致，或与常见 CLI 习惯不同，但核心目的已被可验证的方式覆盖。
- **环境限制**：由本机 Codex 版本或协议决定，不是本项目能修好的。

实测环境：Windows 11、Python 3.11.9、Git for Windows、Codex CLI `0.167.0-alpha.3.2`（ChatGPT 账号已登录）。

## 1. 状态采集主通道是 app-server 通知，`[hooks]` 配置未被 Codex 执行

**现象** — `relay hooks install` 会把 `[hooks.<event>]` 托管块写入 `%USERPROFILE%\.codex\config.toml`，写入后用 `codex app-server --print-startup-config` 校验该文件仍可解析（不通过则自动回滚）；即使写入成功，Codex 也从不执行其中命令：`hooks/list` 返回的注册列表为空，`events` 表里没有任何 `source='hook'` 的记录。给 app-server 传 `--dangerously-bypass-hook-trust` 会被拒绝。

**原因** — 本机实测的 Codex `0.167.0-alpha.3.2` 没有把用户配置里的 `[hooks]` 段注册为可执行 hook（信任/注册机制未对该版本开放），而绕过 hook 信任的启动参数也不被 `codex app-server` 接受。这是环境限制，不是配置写法问题。

**当前替代方案** — 状态采集的主通道是 app-server 通知，全部属于官方协议消息：`turn/completed`、`item/completed`、`thread/tokenUsage/updated`、`thread/compacted`、`hook/started`、`hook/completed`。控制器据此获得轮次、最终消息、token 用量、上下文容量与压缩次数；`make_event_sink` 还会把 `turn/started`、`thread/started`、`thread/compacted`、`hook/*`、`error` 等写入 `events`（`source='appserver'`）。`relay hook --event sessionStart` 这类采集器保留并在 hooks 真正可用时自动生效，报告里两个通道分开统计，`relay hooks status` 同时显示「已写入」与「实际观测到」。

**如何验证** — 依次执行：

```powershell
relay hooks install     # 输出中 "Codex 实际注册的 hook:" 为 [] 即证明未注册
relay hooks status      # observed_events 为 "无"
relay report --chain ch_1a2b3c4d5e6f   # 「Hooks 采集 / Hook evidence」段说明改由通知通道完成
```

## 2. 桌面版 Codex 的可见窗口与自动聚焦未实现

**现象** — 接力发生时不会弹出、切换或聚焦 Codex 桌面版的聊天窗口。会话完全在后台创建，用户在桌面版界面上看不到“自动跳出来的新会话”。

**原因** — 需求把「桌面版自动打开聊天窗口、可见会话切换」列为独立的兼容性任务，允许后台接力先交付；当前实现只使用 app-server 的 `thread/start`，没有驱动桌面版 UI 的能力。

**当前替代方案** — 后台自动接力功能完整可用：新会话是真实的新主线程，能实际执行工作。需要人工查看时用 `relay status` / `relay history` / `relay report` 观察进度，或在 Codex 中按 thread id 自行打开。

**如何验证** — 运行 `relay start ...` 观察桌面版是否出现新窗口（当前不会）；同时 `relay status --chain ch_1a2b3c4d5e6f` 的会话列表会出现序号 1、2、3… 且 `turns` 递增，证明会话真实存在并执行过。

## 3. 真实上下文压力（Level 3）结果未记录，待验证

**现象** — Level 3 的测试入口、判定项与报告生成都已实现，但本文件不提供任何“已通过”结论。

**原因** — 该层必须消耗真实 Codex 额度，并用真实 token 用量跨过阈值，结果随时间、账号额度、模型与网络变化；仓库中没有可复现的当次记录。

**当前替代方案** — 先用零额度的 `relay test --mode mock` 验证状态机与数据链路，再用 `relay test --mode real-handoff` 验证真实会话接力（只模拟阈值）。真实压力验证由人工在合适时机显式执行。

**如何验证** — 执行 `relay test --mode real-pressure`，然后查看 `%LOCALAPPDATA%\CodexPotterRelay\reports\test-real-pressure-<时间戳>.md`：只有其中「真实验证 vs 模拟」段的「真实 token 压力样本数」大于 0、且 `context_pressure` 事件的 `source` 为 `real` 时，才能说真实压力被验证过。在此之前它的状态是**待验证**。

---

## 4. 连续真实交接 A→B→C→D 的结果依赖真实额度，待验证

**现象** — `relay test --mode real-handoff` 与 `relay test-handoff --count 3` 会真实创建 4 个主会话并跑完整接力链，但本文件不宣称它们在某次运行中通过了。

**原因** — 需要真实账号登录与模型额度；不同环境、不同时间的结果可能不同（网络中断、额度耗尽、模型行为差异都会影响结论）。

**当前替代方案** — Level 1 的 mock 场景已覆盖状态机、回滚、幂等与预算保护；Level 2 的判定项写死在代码里，跑一次就会给出 `[PASS]/[FAIL]`，无需人工解读。

**如何验证** — 执行 `relay test-handoff --count 3`，检查输出与报告中的七项判定（会话数、每会话都有 turn、连续交接 `ok`、新会话自动继续、任务全部完成、验收命令通过、模拟值有标记）。任一项 `[FAIL]` 即为未通过，不要只引用“会话创建成功”。

## 5. `prepare` 阈值（0.75）不单独预生成交接包

**现象** — 达到 0.75 时，控制器并不会额外生成一个独立的“交接包文件”快照；它写的是检查点（`reason=pressure:prepare`），真正用于接力的交接包在交接状态机的 `PREPARE` 阶段生成、写盘并回读校验。

**原因** — 每次交接的 `PREPARE` 都会重新写检查点并从磁盘读回校验；若在 0.75 就预生成，等于把同一份内容写两遍，且可能落后于最新代码状态。

**当前替代方案** — 0.75 及以上每轮 turn 结束都会刷新检查点（检查点内含 `HANDOFF.md` 全文与 `state.json`），因此“随时可恢复”的能力在 0.75 就已具备；交接时的那一次写盘还附带校验和检查与链归属校验。

**如何验证** — `relay history --chain ch_1a2b3c4d5e6f --events` 查看 `context_pressure` 事件的 `level=prepare` 与紧邻的 `checkpoint_created`（reason 为 `pressure:prepare`）；`relay report` 的检查点表会列出每个版本与原因。

## 6. 无法测量用量时不做百分比判断（语义差异，非缺陷）

**现象** — 拿不到可靠的 token 用量或上下文容量时，系统不会给出任何占比，也不会用估算值凑出“80%”；此时四个百分比阈值全部不参与判断。

**原因** — 需求明确禁止伪造百分比。比例只在 `thread/tokenUsage/updated` 同时给出使用量（`last.inputTokens + last.cachedInputTokens`）与 `modelContextWindow` 时才计算。

**当前替代方案** — 使用可验证信号回落：观测到压缩事件即按“窗口已满”执行交接（原因文本写明未编造百分比）；距上次检查点达到 `fallback_turn_limit`（默认 40）轮则进入准备级别；否则维持 `ok` 并继续依赖轮次计数。报告中的占比显示为 `n/a`，来源标记为 `unavailable`（`fallback` 常量已预留，但当前样本只会产出 `unavailable`）。

**如何验证** — 查看 `relay report` 的「上下文压力时间线」：`Ratio` 列为 `n/a`、`Source` 为 `unavailable` 的行即为回落样本；`Level` 列显示此时采用的判定。

## 7. `relay status --all` 参数当前不改变输出

**现象** — 该参数被解析器接受，但传入后输出与不传时完全一致。

**原因** — `_cmd_status` 只使用 `--chain`（缺省取最近创建的一条链），`--all` 尚未接线。

**当前替代方案** — 用 `relay chains` 查看全部链列表（最多 100 条），再对目标链执行 `relay status --chain ch_1a2b3c4d5e6f`；需要机器可读输出时用 `relay --json status --chain ch_1a2b3c4d5e6f`。

**如何验证** — 分别执行 `relay status` 与 `relay status --all`，比较输出即可。

## 8. `relay resume` 只改数据库状态，不启动控制器

**现象** — 对暂停的链执行 `relay resume` 后，链状态变为 `running`，但不会有进程继续执行；必须再执行 `relay recover` 或 `relay run --chain ch_1a2b3c4d5e6f`。

**原因** — 当前设计中 `resume` 是纯状态转换命令（`paused → running`），控制器生命周期由 `start` / `recover` / `run` 管理。

**当前替代方案** — 按 `relay resume --chain ch_1a2b3c4d5e6f` → `relay recover --chain ch_1a2b3c4d5e6f` 两步恢复；`recover` 会顺带回收陈旧锁并校验台账。

**如何验证** — `relay resume` 后立刻 `relay status --chain ch_1a2b3c4d5e6f`：状态为 `running`、`模型请求` 计数不变；执行 `recover` / `run` 后请求计数开始增长。

## 9. 执行锁回收只在同主机生效

**现象** — 如果一条链的锁由另一台机器上的进程持有，本机不会把它判定为陈旧锁，`relay recover` / `relay run` 会拒绝接管。

**原因** — `_lock_is_stale` 的设计是：不同主机一律视为可能存活（避免两台机器同时写同一份项目），只有同主机且 pid 已死亡才允许接管。

**当前替代方案** — 确认那台机器上的控制器确已停止后，手工删除 `execution_locks` 中对应行再恢复；单机使用（本项目的主要场景）不受影响。

**如何验证** — `relay recover --dry-run` 会打印每条待恢复链的锁归属；同主机进程被杀后重新 `relay recover` 应能自动接管。

## 10. `scripts\install.ps1 -Codex` 的参数位置与 CLI 不匹配

**现象** — 带 `-Codex <path>` 运行安装脚本会失败：脚本把它拼成 `python -m relay doctor --codex <path>`，而 `--codex` 是**全局参数**，必须写在子命令之前。argparse 报 `unrecognized arguments: --codex ...` 并以退出码 2 结束，脚本随后报 “Codex CLI is not usable”。

**原因** — 安装脚本仍把 `--codex` 当作 `doctor` 子选项传递；CLI 已把它实现为顶层全局参数。

**当前替代方案** — 不使用 `-Codex`，改为：`relay --codex "C:\...\codex.exe" doctor`，或在 `relay.toml` 的 `[controller]` 段设置 `codex_executable`，或设置环境变量 `CODEXPOTTER_CODEX`。脚本其余步骤（pip 安装、PATH、init、可选 hooks）不依赖该参数。

**如何验证** — 不带参数运行 `scripts\install.ps1` 应正常完成；带 `-Codex` 时会复现上述 argparse 报错（已知缺陷，与 Codex 安装无关）。对照实验：`relay doctor --codex X` 报参数错误，而 `relay --codex X doctor` 正常输出体检报告。

## 11. 子 Agent（subagent）不单独写入台账

**现象** — `sessions` 表允许 `role='subagent'`，但控制器只记录 `role='main'` 的主会话；会话内部通过 `$loop` / 子 Agent 完成的工作不会作为独立会话出现。

**原因** — 接力的单位是主会话，子 Agent 的生命周期由 Codex 内部管理，app-server 通知里没有稳定可持久化的子会话标识。

**当前替代方案** — 子 Agent 的产出通过任务台账（`.relay/state.json` 的 `tasks` 与 `evidence`）与 git 提交体现；接力判定只依赖台账 + 验收命令 + git 状态。

**如何验证** — `relay status --chain ch_1a2b3c4d5e6f` 的会话列表只出现主会话序号；`relay history` 中不会出现 subagent 交接记录。

## 12. 单元测试覆盖有限

**现象** — `tests/` 下有 `test_config.py`、`test_db.py`、`test_checkpoint.py`、`test_context_monitor.py`、`test_hooks.py`，覆盖配置解析与校验、数据库与迁移、检查点校验和、上下文压力判定、hooks 托管块；控制器主循环、交接状态机与三层测试执行器没有单元测试。

**原因** — 这些模块的行为强依赖真实 app-server 与真实会话，端到端验证被放在 `relay test` 三层里；单元测试只锁定可以脱离 Codex 验证的纯逻辑。

**当前替代方案** — 改动后先跑 `python -m pytest`（需自行安装 pytest），再跑零额度的 `relay test --mode mock`（12 项判定覆盖状态机、回滚、预算保护与多项目隔离）；涉及真实会话的改动需要 `relay test-handoff --count 1` 冒烟。

**如何验证** — `python -m pytest -q` 的收集数量即覆盖范围；`relay test --mode mock` 的输出是端到端基线。

## 13. 测试临时项目默认删除，只有报告长期保留

**现象** — Level 1/2/3 结束后，`test-workspaces\` 下的临时项目会被删除；要保留需显式加 `--keep-workspaces`。报告无论是否保留项目都会写入 `reports\`。

**原因** — 避免长期堆积临时仓库与其中的 git 元数据。

**当前替代方案** — 需要复盘交接细节时用 `--keep-workspaces` 重跑；历史结论看 `reports\test-<mode>-<时间戳>.md`（内含每个链的检查点、交接链、压力时间线与 hooks 证据）。

**如何验证** — 默认运行后检查 `test-workspaces\` 是否为空；加 `--keep-workspaces` 后同一目录会留下带时间戳的项目目录。

## 14. 依赖 Codex app-server 的协议字段，随版本可能变化

**现象** — 交接、压力采样与审批应答依赖若干协议字段：`thread/start` 的 `approvalsReviewer`、`thread/tokenUsage/updated` 的 `modelContextWindow`、`turn/completed` 的 `turn.status`、`hooks/list` 的返回结构等。

**原因** — Codex 仍在快速迭代，本机实测版本为 `0.167.0-alpha.3.2`；字段命名或语义可能在后续版本调整。

**当前替代方案** — 关键判定都做了“缺字段即降级”处理：没有 `modelContextWindow` 就不计算比例、没有 `hook/started` 就不声称 hooks 生效、`thread/start` 缺 thread id 直接报错而不是继续。升级 Codex 后先跑 `relay doctor` 与 `relay test --mode mock`，再跑一次 `relay test-handoff --count 1` 冒烟。

**如何验证** — 升级后执行 `relay test --mode mock`；若真机行为异常，查看 `logs\appserver-<chain_id>.log` 与 `logs\controller.jsonl` 中的原始通知记录。

## 15. 全局参数必须写在子命令之前

**现象** — `relay status --json`、`relay doctor --codex X` 这类写法会被 argparse 拒绝（`unrecognized arguments`，退出码 2），因为 `--config` / `--db` / `--codex` / `--json` 都是顶层参数。

**原因** — 参数解析采用「主解析器 + 子解析器」结构，子命令之后的参数只由子解析器解析；子解析器没有定义这些全局选项。

**当前替代方案** — 把全局参数前移：`relay --json status --chain ch_1a2b3c4d5e6f`、`relay --db PATH chains`、`relay --codex PATH doctor`。编写脚本时固定采用「全局参数在最前」的形式。

**如何验证** — 分别执行 `relay status --json` 与 `relay --json status`，前者报参数错误、后者输出 JSON。
